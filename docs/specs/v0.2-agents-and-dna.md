# lectern v0.2 — agents on demand, source-resolved answers, and the conceptual DNA of a deck

> Status: approved by the owner on 2026-11-16, not started. The target is tag `v0.2.0`.
> Builds on v0.1.0 (`4e4af64`). Licence: MIT. Stays small: every phase keeps `make check` green and
> stays within the size budget in §9.

## 1. Why

v0.1.0 shows that every slide can have its own agent. v0.2 shows three more things:

1. **Agents created as needed, from one design.** A single `AgentSpec` (context, behaviour, model,
   tools) is instantiated on demand and overridden per deck, slide or request. Answering one question
   can launch several research agents in parallel in the background. Each answer still lands on the
   slide that was asked.
2. **Knowing where not to look.** Before any search runs, a fast triage reads the question and
   decides three things: whether to engage, which sources to consult and which to skip, and whether
   any source is likely to hold the answer. Each source's answer carries its own confidence; the
   answers are fused, and the agent answers, qualifies, asks or abstains. (The formalism is §6, from
   the owner's note *Knowing Where Not to Look: query- and source-resolved confidence for agents*.)
3. **The conceptual DNA of a slide and of a deck.** People and AI tools record what shaped a slide:
   ideas, reasoning, notes, citations and references (images, PDFs, links). Each record has a scope
   (one slide, several slides or the whole deck) and a degree of influence. lectern renders that
   DNA as a trace, both visually and as text. The agents use it as context and cite it.

## 2. Glossary (add to `docs/glossary.md`)

- **AgentSpec**: the one document that defines an agent: its context sources, behaviour, model
  binding, tools and budget. Every agent is an instance of a spec plus its overrides.
- **Instance**: one agent run, created for one job from a resolved spec.
- **Job**: one question, asynchronous. It has a status (`queued → triaging → researching → fusing →
  answered | abstained | asked | failed`), a slide (or the deck) it answers on, and a trace.
- **Researcher**: an instance that reads one source for one job. Several run in parallel.
- **Source**: where evidence comes from. `P` is the model's own knowledge. `W` is the open web (Exa
  search and URL fetch) and the user's own turns. `K` is the deck plus its DNA plus the author's
  uploads (the trusted base). `M` is lectern's memory (past questions, answers and feedback).
- **Triage**: the step before execution: hurdle, routing and coverage class (§6.1). It uses jev when
  an OpenRouter key is set, and rules otherwise.
- **Influence**: one DNA record (§7).
- **Degree**: how strongly an influence shaped its target: `high`, `medium`, `low` or `general`
  (background that shaped the deck as a whole).

## 3. Users and surfaces

| Who | Surface | What they do |
|---|---|---|
| Viewer | Web app | Ask any slide or the deck; watch the job's progress; read the answer with per-source confidence and citations; open the DNA trace |
| Author | Web app | Everything a viewer does, plus add, edit and remove influences and references on a slide, a subset of slides or the whole deck |
| AI tool (Claude, Codex, …) building a deck | MCP | The same as an author: add reasoning, citations, influences and references while it builds; read the DNA; ask questions |
| Scripts | REST API, CLI | The same as MCP |

**Parity rule:** UI, REST, MCP and CLI call one service layer (`service.py`), so nothing is
possible in one surface that is impossible in another.

## 4. AgentSpec and overrides (P0)

```yaml
# backend/lectern/agents/default.yaml (packaged)
id: slide-agent
persona: "Explain this slide the way its presenter would."
behaviour:
  rules: ["Answer only from evidence; cite every sentence.", "Say so when unsure."]
  decision: {answer_at: 0.5, qualify_band: 0.15, ask_when: ambiguous}   # §6.4
context: [slide, notes, neighbours, deck_outline, dna, attachments]
model: {provider: fake, model: null, api_key_env: null}                # anthropic | openai_compat | fake
tools: [deck_search, dna_search, memory_search]                        # + web_search, fetch_url when enabled
triage: {provider: rules}                                              # jev when OPENROUTER_API_KEY is set
budget: {max_researchers: 4, max_seconds: 60, max_tool_calls: 12}
```

- **Layers, applied in order:** packaged default → `deck.agent` → `slide.agent`, where an HTML deck
  can set it with `data-agent='{…}'` and the API/MCP can store it → `request.agent`, which only
  allows a safe subset: persona, model (from the allowlist), tools (a subset of the deck's) and
  budget (lower only). A merged spec is validated: unknown keys are refused (pydantic
  `extra="forbid"`).
- **The model binding is per instance.** The key is read from the environment variable the spec
  names, never stored in the database or returned by the API. A request may pick a model only from
  `LECTERN_MODEL_ALLOWLIST`.
- `GET /agents/resolve?deck=&slide=` shows the effective spec, with each field's layer and the key
  shown only as set or unset.

**AC-P0.**
1. Overrides merge in that order, and an unknown key is a 422.
2. Two slides of one deck answer with different personas and models.
3. A request override cannot raise the budget or add a tool the deck has not enabled.
4. Keys never appear in any response, trace or log (test with a sentinel key).

## 5. Asynchronous parallel agents (P1)

- `POST /decks/{d}/slides/{n}/ask` (and `/decks/{d}/ask` for the deck) returns `202 {job_id}` at
  once. The job runs as an `asyncio` task in the API process. There is no external queue; jobs are
  rows in SQLite, and a restart marks running jobs `failed: interrupted`.
- **Graph per job:** `triage → plan → research (fan-out) → fuse → decide → answer → cite → persist`.
  - `research` starts one researcher instance per chosen source with `asyncio.gather` (bounded by
    `budget.max_researchers`). Each researcher runs a small tool loop on its source. It returns
    evidence blocks plus that source's answer, its reliability `r_s` and its ghost mass `g_s`.
  - The existing `cite` revise loop stays.
- **Progress streams** over SSE: `GET /jobs/{id}/events`, one event per step and per researcher.
  The UI shows the researchers as parallel lanes. Many jobs on many slides run at once, and each
  answer is posted to its own slide's thread (`slide_messages`), never to whichever slide is open.
- **Cancellation:** `DELETE /jobs/{id}`.
- **Budget:** a wall-clock limit and a tool-call limit per job. When either is hit, the job fuses
  whatever evidence it has and says it ran out.

**AC-P1.**
1. Three jobs on three slides, started together, overlap in time (a fake provider with delays), and
   each answer lands on its own slide.
2. Two researchers of one job run concurrently.
3. SSE replays from `Last-Event-ID`.
4. A cancelled job stops its researchers.
5. A restart marks running jobs interrupted.

## 6. Triage, per-source confidence, fusion and decision (P2)

### 6.1 Triage (before any source is searched)

From the question alone (plus cheap metadata such as deck outline hits, DNA hits, memory hits and
entity popularity, when available), triage returns:

- `engage: P(engage)`: the hurdle π(q). Out of scope, ill-posed or false-premise questions are
  declined or reframed here, before any source runs.
- `route`: for each source s ∈ {P, W, K, M}, consult or skip, with a short reason ("K holds the
  slide's figures; W is unnecessary").
- `class`: `covered | rare | ghost`, with probabilities. A ghost means no source is likely to hold
  the answer, so the agent derives the answer in the open, asks, or abstains.
- `hops`: the estimated inferential distance d (0 means a lookup).

**jev transport** (when `OPENROUTER_API_KEY` is set):

- Request: `POST https://openrouter.ai/api/alpha/decisions` with body `{state, model, questions}`,
  where `model` is `typesafe/jev-1.13-20260917` (overridable with `LECTERN_JEV_MODEL`). The answer
  is `{model, answers, usage}`.
- Questions use the `noul` type, which gives P(true) in [0, 1], and `choice` with `criteria`.
- `state` is a compact JSON object of at most 2 KB: the question plus the probe counts. It never
  contains the whole deck.
- Timeout is 8 s. On any error, fall back to the rules triage and record which one ran in the trace.

The rules triage is the offline default and the one tests use. It uses keyword and probe heuristics:
K hits above a threshold mean `covered`; a recency word with no K hit routes to W; and so on.

### 6.2 Per-source answers

Each researcher returns `(ŷ_s, r_s, g_s, evidence)`.

- `r_s` is the source's reliability given that the answer is in its corpus. It is a per-source
  prior, adjusted by retrieval agreement (for W, agreement among the top-k snippets) and by
  memory's track record on similar questions (for M).
- `g_s` is the probability that the answer is not in the source's corpus at all.
- Both are reported, never hidden.
- **P** is the model answering closed-book.
- **W** uses Exa search (`POST https://api.exa.ai/search`, header `x-api-key: $EXA_API_KEY`, body
  `{query, numResults, contents: {text: true}}`) and `fetch_url` (httpx, size-capped, text only).
- **K** is BM25 over the slides, notes, DNA and attachments. A DNA influence's degree weights its
  blocks: high 1.0, medium 0.6, low 0.3, general 0.2.
- **M** is BM25 over past answered jobs and the feedback on them (👍/👎 on an answer).

### 6.3 Fusion

Both rules are computed and shown side by side in the trace.

- **Bayesian:**
  `p(y|e) ∝ p0(y) ∏_s [(1−g_s)(r_s p_s(y) + (1−r_s)u(y)) + g_s u(y)]` over the candidates plus an
  outside option ∅ ("none of these"). The evidence Z is reported.
- **Dempster–Shafer:** simple support functions `m_s({ŷ_s}) = r_s`, `m_s(Θ) = 1−r_s`, combined by
  Dempster's rule. The conflict κ is reported, never just absorbed (Zadeh's counterexample).
- Candidates are clustered by normalised answer text. With a real model, a cheap equivalence check
  merges paraphrases.

### 6.4 Decision

- `answer` when the fused P(best) is above 0.5.
- `qualify` when it is within `qualify_band` of 0.5.
- `ask` a clarifying question when triage's ambiguity dominates.
- `abstain` otherwise, saying which sources were checked and why none holds the answer (ghost).

The answer shows a confidence chip per source and the fused figure; hovering shows `r_s`, `g_s`, Z
and κ.

**AC-P2.**
1. With faked sources:
   - a covered question is answered from K, and W is skipped;
   - a fresh question routes to W;
   - a ghost question abstains and names the ghost;
   - contradicting K and W give a high κ and a `qualify`.
2. The jev transport is tested with a fake HTTP server, including the timeout fallback.
3. Unit tests check the Bayesian and Dempster–Shafer maths against hand-computed cases.

## 7. Conceptual DNA (P3 model + REST + UI, P4 MCP)

### 7.1 Model

```text
Influence
  id, deck_id
  scope:     {kind: slide|slides|deck, slides: [n…]}       # one slide, a subset, or the whole deck
  target:    {component: whole|text|image|chart|layout|concept|element, element_id?: str, label?: str}
  kind:      idea | reasoning | explanation | note | citation | reference
  degree:    high | medium | low | general
  title, body (markdown, ≤ 10k chars)
  refs:      [{type: url|file, url?, file_id?, label?, quote?}]
  author:    {type: human|ai, name, tool?, model?}            # e.g. ai / Claude / claude-opus-5-5
  via:       ui | api | mcp | cli
  parent_id? (an influence derived from another), created_at, updated_at
File: id, deck_id, name, mime (image/*, application/pdf, text/*), size ≤ 20 MB, sha256, text (extracted)
```

- **Element ids:**
  - HTML decks: `data-lectern-id` attributes (ingest assigns stable ids to `h1`–`h3`, `img`,
    `figure` and `table` when they are missing);
  - pptx: shape ids;
  - Google Slides export: object ids.

  The UI lets an author click an element on the slide to set `target.element_id`.
- **Extraction:** PDF text with `pypdf` (BSD); image captions from the influence's own title and
  body (no OCR in v0.2). Extracted text is indexed into K with the influence's degree weight.
- **Edit rights:** influences are append-mostly. Each edit keeps the previous body in
  `influence_history`.

### 7.2 REST and UI

- REST:
  - `POST/GET/PATCH/DELETE /decks/{d}/influences` (filter by `slide`, `kind`, `degree`, `author`);
  - `POST /decks/{d}/files` (multipart);
  - `GET /decks/{d}/dna` and `/decks/{d}/slides/{n}/dna`. These return the DNA graph: nodes
    (deck, slides, components, influences, files, external refs) and edges (influences → target,
    derived-from, cites).
- **"+ New influence"** (top-right button → drawer):
  - scope picker: this slide, choose slides (multi-select from the rail), or whole deck;
  - target picker: whole slide, or click an element; kind; degree;
  - title and body;
  - references: add URL, upload image/PDF/text, or pick an existing file.

  This is the same form the API and MCP fill.
- **DNA panel per slide and for the deck**, two views:
  - **Visual:** a layered SVG graph with no graph library. Deck-wide `general` influences are at
    the top, then slide-scope influences, then components, then the slide. Edge weight and colour
    show degree. Clicking a node opens its drawer.
  - **Textual:** an ordered trace ("This slide's revenue chart was shaped by: (high) the Q3 board
    memo [pdf p.4], reasoning by Claude; (medium) …"), with citation chips that jump to the
    reference.
- The answer trace links to the DNA: when an agent cites an influence, the chip opens it.

### 7.3 MCP server (P4)

The MCP server is `lectern mcp` (stdio) and `/mcp` (streamable HTTP on the API). It uses the
official MIT `mcp` Python SDK and calls `service.py` only.

| Tool | Does |
|---|---|
| `list_decks`, `get_deck`, `get_slide` | Read, including element ids, so an AI can target a component |
| `create_deck` (upload HTML/pptx as base64 or a URL) | The same as the upload UI |
| `add_influence` | One record for a slide, a subset of slides (`slides: [2,3,5]`) or the deck; `author` is filled from the MCP client info plus an optional `model` |
| `add_influences` | A batch, so an AI that builds a deck can log the DNA of every slide in one call |
| `update_influence`, `remove_influence`, `list_influences` | |
| `upload_file` (base64, ≤ 20 MB), `add_reference` | Attach references |
| `get_dna` (slide or deck; `format: graph|text`) | Read the DNA |
| `ask` → `job_id`; `get_job` (status, answer, per-source confidence) | Async questions |

The MCP surface is optionally gated by `LECTERN_MCP_TOKEN` (bearer), and it is open on localhost
when unset.

**AC-P3/P4.**
1. An influence added through the UI, REST and MCP is the same row shape.
2. A subset scope shows on exactly those slides.
3. A PDF reference's text is searchable in K and is cited in an answer.
4. Degree weights change retrieval order.
5. The DNA graph endpoint matches a golden file.
6. The MCP tools are listed and round-trip in a test with the SDK's in-memory client.
7. Vitest covers the drawer form (scope picker, element pick, degree), the visual graph (node
   count and edge weights) and the text trace.

## 9. Constraints

- **Offline by default.** With no keys set, everything works: the fake model, rules triage, and the
  W tools disabled, shown as "skipped: no key". Tests never touch the network: Exa, OpenRouter and
  model providers are faked behind one `http` port.
- **Smallest possible.** New runtime dependencies are only `mcp` (MIT) and `pypdf` (BSD). `httpx`
  is already present through FastAPI's test client; make it a direct dependency only if needed.
  No graph or visualisation library.
- **Size budget**, enforced by `scripts/loc_budget.py`: backend ≤ 3,800 LOC (from 2,400) and
  frontend ≤ 2,600 LOC (from 1,600), tests excluded. If a phase needs more, cut before raising the
  budget.
- **No secrets** in the database, traces or logs. Keys are named per spec and read from the
  environment.
- **Text:** keep the forbidden-path and forbidden-text checks green. The repo must not name the
  private simulator or its engine.
- **Licences:** MIT for the code. Every new dependency must be MIT/BSD/Apache.
- Node 22, uv and pnpm as in v0.1.

## 10. Out of scope for v0.2

- Multi-user accounts and auth beyond the optional MCP token.
- Vector search; BM25 stays.
- OCR of images.
- Agents that edit slides.
- Learned triage. The note's KAP feature classifier and per-cell conformal prediction are a
  research follow-up; v0.2 logs the triage features and outcomes per job (`/jobs.jsonl` export) so
  that a later classifier can be trained.
