# lectern v0.2 — decisions on the spec's open edges

Decisions made while implementing `v0.2-agents-and-dna.md`. Newest last.

## D1. File registry: a permanent id, with the path as a renamable alias (owner, 2026-11-16)

The owner added a requirement: AI tools (over MCP) and people create, read and overwrite slides and
references as files, and their metadata must survive overwrites, renames and deletions.

- **Every file is a blob.** Slides, deck files and references (images, PDFs, text) all live in one
  blob store behind a `BlobStore` port. The default store is a local folder (offline, used by tests).
  S3 or an S3-compatible store (MinIO, R2) is chosen with environment variables and installed as the
  optional extra `lectern[s3]` (boto3, Apache-2.0). This is the one dependency beyond `mcp` and `pypdf`,
  and the owner approved it.
- **Everything else is a SQLite row.** `files(id, deck_id, path UNIQUE, sha256, size, mime, version,
  status live|missing, updated_at)`. Metadata (title, notes, agent override, influences) points at
  the permanent `id`, never at the path. Callers address files by relative path, and lectern resolves
  it to the id.
- **Overwrite** keeps the id, replaces the blob and adds 1 to `version`. Each influence stores the
  `file_version` it was written for, so the DNA trace can flag "written for v2, now v4". Old blobs are
  not kept (no version history in v0.2).
- **Rename through lectern** (`move`, from the UI, REST, MCP or CLI) changes only the path.
- **Rename or delete outside lectern:** `reconcile` (on demand) marks rows whose blob is gone as
  `missing` and lists blobs that have no row. An unregistered blob with the same sha256 is suggested
  as the renamed file. The UI's **Unlinked** list offers "Relink to file…" or "Delete metadata".
- **Slide unit:** a new deck is a folder prefix and each slide is one file in it
  (`decks/q3/03-revenue.html`), ordered by path unless metadata sets an order. Uploaded `.pptx` and
  single-file HTML decks stay one blob, and a slide in them is addressed as `path#n`.
- **Extra MCP tools** (with REST, UI and CLI parity): `put_slide(path, content, mode=create|overwrite)`,
  `read_slide(path)` (content, metadata and DNA), `update_slide_meta`, `move`, `delete`, `reconcile`.
- **Out of scope:** S3 event notifications, blob version history, multi-user accounts.
- **Where:** the registry lands in P3 together with the DNA model, because influences target its ids.

## D2. AgentSpec details (P0)

- **JSON, not YAML.** The packaged default is `backend/lectern/agents/default.json`, so no YAML
  dependency is needed. Deck and slide layers are JSON objects too (`data-agent='{…}'`, or
  `PUT /decks/{d}/agent` and `PUT /decks/{d}/slides/{n}/agent`).
- **An `env` layer** sits between the default and the deck. It carries v0.1's `LECTERN_PROVIDER`,
  `LECTERN_MODEL` and `LECTERN_BASE_URL`, so an existing `.env` keeps working.
- **Persona attributes stay.** A deck's or slide's `persona` (`data-persona`) is applied on top of
  its `agent` layer.
- **A request model choice** is `provider:model`, and it must be in `LECTERN_MODEL_ALLOWLIST`
  (comma-separated). `fake` is always allowed. When the request changes the provider, the
  `api_key_env` and `base_url` reset to that provider's defaults, so one provider's key is never sent
  to another.
- **Lists are replaced, not merged**, when layers merge (objects merge key by key).
- **Providers keep the key out of `repr`**, so a logged provider never shows it.

## D3. Jobs (P1)

- **Asking always makes a job.** `POST …/ask` returns `202` with the queued job. `?wait=true` waits
  and returns the finished job in the same response (for scripts and tests). The command-line
  `lectern ask` stays synchronous.
- **History comes from the slide's thread** (`slide_messages`, the last 6 turns), not from the
  client, so every surface sees the same conversation.
- **One more terminal status, `cancelled`**, in addition to the spec's list.
- **Researchers are threads.** Each researcher is a plain function run with `asyncio.to_thread`.
  Cancelling a job cancels its tasks at once. A thread that is already inside a model call finishes
  in the background, but its result is discarded and never reported.
- **New block ids** for the new sources: `mem:<job id>` (memory) and `model:closed-book` (P).
- **SSE event kinds:** `status`, `triage`, `researcher`, `budget` and `done`. Every event carries
  `t`, the job manager's clock reading.

## D4. Triage, confidence and the decision (P2)

- **`triage.provider` gains `auto`, the new default:** jev when `OPENROUTER_API_KEY` is set,
  otherwise rules. `rules` forces the rules even with a key; `jev` asks for jev (it still falls back
  to rules on any error).
- **jev may only narrow the rules' route.** It can skip a source but cannot enable a tool or a
  source with no key. The jev question set is `engage`, `consult_{K,W,P,M}`, `ambiguous` (`noul`)
  and `coverage` (`choice` with criteria). The answers are read defensively, and any surprise falls
  back to rules.
- **Triage's ghost probability is the Bayesian prior on ∅** ("none of these"). The rest of the
  prior is spread evenly over the candidates, so triage and fusion are linked. With no triage (unit
  tests), the prior is uniform.
- **A source that found nothing votes for ∅.** That's how a ghost question abstains.
- **Heavy conflict qualifies.** κ ≥ 0.5 qualifies the answer even when the Bayesian P(best) is
  above 0.5. The spec's AC-P2 needs contradicting K and W to qualify, and it says κ is never just
  absorbed.
- **The hurdle:** `engage < 0.5` abstains before any source runs ("out of scope or ill-posed").
  Under the rules that means a question with no content words.
- **The K researcher searches with the question alone.** It doesn't add the slide title, so it
  can't "find" the current slide for an unrelated question. The answer graph still puts the slide
  in context.
- **Reliability and ghost mass:**
  - K: r = 0.9; g comes from its best BM25 score s, g = max(0.05, 1 - s/(s+2)).
  - M: r = 0.3 + 0.6·(1+👍)/(2+👍+👎) over the matched past jobs.
  - W: r = 0.4 + 0.4·agreement, where agreement is the share of snippets with two or more of the
    answer's content terms.
  - P: r = 0.5, g = 0.5.
- **Feedback:** `POST /jobs/{id}/feedback {vote}`. The `/jobs.jsonl` export has one line per job:
  triage features and probes, route, verdict, p_best, κ, Z and feedback.
- **One network port** (`lectern/http.py`) for jev, Exa and `fetch_url` (http(s) only, text only,
  200 KB cap). The model providers keep their own httpx calls, as in v0.1.
- **Size budget:** the backend budget rose from 2,400 to 3,000 in this phase (the spec allows up
  to 3,800).

## D5. The jev wire format, aligned with production use (2026-11-16)

- `questions` is an object keyed by question id. Each `noul` has `instructions` and
  `criteria: {true, false}`; `coverage` is a `choice` whose `criteria` maps each option id to its
  meaning.
- Each answer is `{noul: p}` or `{choice: id, confidence: c}`. A `noul` outside [0, 1] (or not a
  number), or an unknown choice, makes the reply unusable, and triage falls back to the rules.
- 429 and 529 are retried once. 401, 402, 403, 404 and transport errors fall back to the rules. A
  422 also falls back, but the trace note names it a request bug.
- Headers: `Authorization: Bearer <key>`, `Content-Type: application/json`, `X-Title: lectern`.
- The chosen coverage class gets the reply's confidence; the other two share the rest equally.

## D6. The DNA, the registry and folder decks (P3)

- **One facade, `hub.py`, for every surface.** REST (`dna/routes.py`) and MCP call it, so parity is
  enforced by construction. `FileError` carries an HTTP status, and one exception handler maps it.
- **Slides are referred to by lasting ids.** A folder deck's slide is its file id; any other slide
  is `<deck file id>#<n>` (or `deck-<id>#<n>` for decks uploaded before v0.2). Influences store
  these ids, and `scope.slides` (the numbers) is recomputed on every read, so reordering a folder
  deck keeps the DNA on the right slide.
- **Uploaded decks keep their original** at `uploads/<deck id>/<name>`. References uploaded for a
  deck go to `refs/<deck id>/<name>`.
- **A folder deck's slide metadata** (`title`, `notes`, `order`, `persona`, `agent`) lives in the
  slide file's metadata, because its slide rows are rebuilt from the files after every change.
- **Versions count content changes.** Relinking or re-putting identical bytes keeps the version.
  Each influence stores `versions` (file id → version it was written for); the graph marks it
  `stale`, and the text trace says "⚠ written for v1 of …, now v2".
- **Deleting keeps the metadata.** `DELETE /file` marks the file `missing`, so it shows in the UI's
  unlinked list (relink, or delete metadata). `?purge=true` forgets it at once.
- **Element ids:** HTML ingest gives `h1`–`h3`, `img`, `figure` and `table` a stable
  `data-lectern-id` (`img-1`, …). In pick mode the sandboxed slide posts the clicked id to the
  page; the page accepts only `[\w.-]{1,200}`, and only while picking. Element ids for pptx shapes
  and Google Slides objects are **deferred**; for those, `target.label` names the part in words.
- **K search** puts the DNA (title and body) and the pages of referenced files into K, ranked by
  BM25 × degree weight, with block ids `dna:<id>` and `file:<id>:p<page>`. Citation chips open the
  record or the DNA panel.
- **Tests and throwaway apps** use `MemoryBlobs`. `create_app` without a store uses
  `LECTERN_BLOBS`.
- **Size budget:** the backend budget is now 3,800, the spec's cap.

## D7. The MCP server (P4)

- **SDK:** the official `mcp` Python SDK 2.x (MIT), where FastMCP is now `MCPServer`. The tools are
  the public methods of `mcp_server.Tools`. Their input schemas are generated from the Hub's
  pydantic models (`InfluenceIn`, `InfluencePatch`, `Ref`), so nothing is written by hand.
- **24 tools:** the spec's 14, plus D1's `put_slide`, `read_slide`, `update_slide_meta`, `put_file`,
  `read_file`, `list_files`, `move_file`, `delete_file`, `reconcile_files` and `relink_file`.
- **Authorship:** `author` comes from the MCP client's `clientInfo.name` plus an optional `model`
  argument; `via` is `mcp`.
- **Errors:** lectern's own errors (not found, conflict, bad path, refused layer) come back as tool
  errors with a readable message, so the AI can correct itself.
- **`ask` is async** so its job runs on the server's event loop; `get_job` polls it.
- **Transports:** stdio is `lectern mcp`; streamable HTTP is mounted at `/mcp/` on the API (the
  SDK's DNS-rebinding protection accepts localhost hosts). `LECTERN_MCP_TOKEN` gates only `/mcp`,
  using a constant-time compare.
- **CLI parity:** `lectern put-slide`, `add-influence`, `dna` and `reconcile` go through the same
  Hub.
- **Size:** trimmed, not raised. `load_deck` and `spec_errors` were replaced by `hub.deck` and one
  exception handler (FileError, SpecError, IngestError), and `create_app` now takes `build_hub`'s
  arguments. The backend is 3,786 of 3,800.

## D8. The demo and the last fixes (P5)

- **The demo deck** is a folder deck, `decks/knowing-where-not-to-look/` (6 HTML slides and a
  reference summary of the note). `scripts/demo.py` (`make demo`) plays the AI author: over MCP
  (the SDK's in-process client, introducing itself as "lectern demo (a scripted AI client)") it puts
  the slides, uploads the reference, logs 8 DNA records in one batch (deck-wide, per slide and on
  elements), prints a slide's trace, and asks three slides in parallel: two are answered, one
  abstains as a ghost. It is safe to re-run: the slides refresh, and the DNA is logged once. The
  deck leaves out the note's section on its exercise environment.
- **Paraphrases merge in fusion.** Answers that share at least half their content words are one
  candidate. Without this, the fake model's extracts from K and M disagreed on wording alone and
  every answer came out qualified (found in a live run).
- **HTML table cells** are read as `a | b | c`. Before, adjacent cells ran together.
- **The text trace** says "for slide 2", not "for slides 2", when one slide is in scope.
- **Version 0.2.0** in `pyproject.toml` and the API.

## D10. Deployment artifacts and production safety (owner, 2026-11-16)

- **One image** (`Dockerfile`): a Node 22.21 stage builds the web app; a Python 3.12.12 slim stage
  runs `lectern serve --host 0.0.0.0` as a non-root user (uid 10001). It serves the built app from
  `LECTERN_STATIC` and the API on the same port. The web app's `/api/*` calls are mapped to the API
  in-process. There is a healthcheck on `GET /health` (new). The base images and uv are pinned to
  exact versions. `EXTRAS=s3` adds boto3.
- **`deploy/compose.yml`:** binds `127.0.0.1:${LECTERN_PORT:-8790}`, with volumes for the database
  and the blobs, `env_file` `.env`, and `restart: unless-stopped`. It sets `LECTERN_PUBLIC=1` and
  `LECTERN_TRUST_PROXY=1`, and requires `LECTERN_HOSTS`.
- **`deploy/nginx.conf.template`:** an envsubst template with IPv4 listeners only and no `http2` on
  the listen lines. SSE and `/mcp` are unbuffered. `client_max_body_size 21m`.
- **The guard (`guard.py`):**
  - `LECTERN_PUBLIC=1` refuses to start without `LECTERN_MCP_TOKEN`.
  - `LECTERN_SITE_PASSWORD` adds a login page and an HttpOnly session cookie (an HMAC of the
    password); `/mcp`, `/health` and `/login` are exempt.
  - Per-IP sliding-window limits on asks and uploads. IPs come from `X-Real-IP` only behind a
    trusted proxy.
  - The `Content-Length` cap is enforced before a body is read.
  - The values of `*_KEY`, `*_TOKEN` and `*_PASSWORD` variables are redacted from log records.
- **The daily ask budget** (`LECTERN_MAX_ASKS_PER_DAY`, default 200) lives in the job manager, so
  REST, the web app, MCP and the CLI all count against it (429, or a tool error over MCP).
- **MCP behind a proxy:** the SDK's DNS-rebinding protection now allows the names in
  `LECTERN_HOSTS` plus localhost. Without this, nginx-forwarded MCP requests get a 421.
- **Validation:** checked offline. `docker compose config` parses, and a local run of the image's
  command with the built app covers `/health`, the login flow, the token refusal, the `/mcp` 401
  and log redaction. The image itself was **not built** here: the workstation rule is not to start
  containers.
- **Size budget:** the backend cap is now 4,100 (D1 plus D10), within the ceiling ae gave.

## D9. System1 resolves from the existing configuration (owner, 2026-11-16)

System1 is the fast decision model behind triage. `jobs/system1.py` resolves it in this order,
and the resolution is shown in the trace (`confidence.triage.system1`) and in `/agents/resolve`
(`system1`): its kind, provider, model, the key's variable name, key `set`/`unset` (never the
value), and why.

1. **Explicit:** `SYSTEM1_MODEL_PROVIDER` (openrouter | openai | google | anthropic |
   openai_compat), `SYSTEM1_API_KEY`, `SYSTEM1_MODEL_NAME`, optional `SYSTEM1_BASE_URL`.
2. **The main provider is OpenRouter.** That is `LECTERN_PROVIDER=openrouter`, a base URL on
   `openrouter.ai`, or `openai_compat`, whose default base URL is OpenRouter. Then jev runs with
   `LECTERN_API_KEY` (the owner's configuration), unless `SYSTEM1_MODEL_NAME` names another
   `provider/model`, which then runs as a structured System1 on OpenRouter. `OPENROUTER_API_KEY`
   also enables jev.
3. **OpenAI, Google, Anthropic** (by provider, or by the host of an `openai_compat` base URL), or
   any other OpenAI-compatible host. None of them offers a decisions endpoint, so a **structured
   System1** runs on the same key with `SYSTEM1_MODEL_NAME`, else `LECTERN_MODEL`. Its JSON
   schema mirrors jev's answers (`{qid: {noul}}`, `{coverage: {choice, confidence}}`), so one
   function (`triage.from_answers`) handles both:
   - OpenAI-compatible: `response_format` json_schema, strict;
   - Gemini: `generateContent` with `responseSchema` (without `additionalProperties`, which
     Gemini's OpenAPI subset rejects);
   - Anthropic: a forced `system1` tool call.
4. **Otherwise the rules.** An explicit provider with no key, or with no model for a structured
   System1, also falls back to the rules, and the `why` says which.

`triage.provider: rules` in an AgentSpec still forces the rules. 429 and 529 are retried once for
every System1, and any other failure falls back to the rules with a note such as
`structured:openai failed (JSONDecodeError)`.

Also in this change: the test sentinels no longer look like keys (`test-sentinel-key-not-real`,
`test-sentinel-token`). `gitleaks dir` reports nothing in the repository's files; its three
findings are in the git-ignored `.env`. The tests budget rose from 2,500 to 2,700 for the D9 and
D10 tests (the spec sets no tests budget). The backend is 4,099 of 4,100, after trimming
`jobs/rows.py`, `jobs/routes.py` and `triage.py`.

## D11. User accounts, invites and personal MCP tokens (owner, 2026-11-16)

The owner asked for a login like the one in the system lectern runs alongside: only invited
users, admins who add users, a seeded first admin, and personal MCP tokens kept in SQLite.

- **Login is on** with `LECTERN_AUTH=1` or `LECTERN_PUBLIC=1` (compose sets the latter). It
  replaces D10's shared site password and `LECTERN_MCP_TOKEN`, which are gone.
- **Invites:** an admin invites an email address (Account → Users) and gets a one-time link,
  `/#invite=<token>`. The token is in the URL fragment, so it never reaches a server log. The
  invitee opens the link and chooses a password (at least 12 characters). A new link voids the old
  one, and that is also how an admin resets a forgotten password. lectern sends no email.
- **The first admin** is seeded with `lectern users create-admin <email>`, which prints the link.
  It is safe to re-run while that admin is still invited, and refuses once the account is active.
- **Storage:** tables `users`, `sessions`, `invites` and `access_tokens`. Passwords use scrypt from
  the standard library (no argon2 dependency). Session, invite and access tokens are random; only
  their sha256 is stored.
- **Sessions:** an HttpOnly, SameSite=Strict cookie (Secure when public) that lasts 14 days, plus a
  CSRF token derived from the session and required as `X-CSRF-Token` on every write. Login is
  rate-limited per IP. Five wrong passwords lock an account for 15 minutes. An unknown email and a
  wrong password take the same work and give the same answer.
- **Roles:** `admin` and `member`. Admins invite, change roles, disable (which ends the user's
  sessions at once) and issue new links. lectern keeps at least one active admin.
- **Personal access tokens** (`lectern_pat_…`, Account → MCP tokens): named, valid for 1 to 90
  days, shown once, revocable, with their last use recorded. Each request resolves the owner
  again, so a disabled user's tokens stop at once. MCP influences are authored
  "<client> for <email>".
- **What stays open:** the web app's static files (it renders the login form), `/health`,
  `/auth/login`, `/auth/accept-invite` and `/auth/me`. With login off (local use), everything is
  open as before, the settings page is available to the one local user, and `/mcp` is open on
  localhost.

## D12. The model, System1 and API keys, managed from the web app (owner, 2026-11-16)

- **Admins edit settings** under Account → Models and keys: `LECTERN_PROVIDER`, `LECTERN_MODEL`,
  `LECTERN_BASE_URL`, `LECTERN_MODEL_ALLOWLIST`, the `SYSTEM1_*` settings and `LECTERN_JEV_MODEL`.
  They also store the keys `LECTERN_API_KEY`, `SYSTEM1_API_KEY`, `OPENROUTER_API_KEY` and
  `EXA_API_KEY`.
- **Keys are encrypted** with Fernet (from `cryptography`, already present through `mcp`; now a
  direct dependency) under `LECTERN_SECRET_KEY`. Without that key, keys can only come from the
  environment and storing one answers 503.
- **The API never returns a key**: only set or unset, its source (lectern, environment or unset)
  and its last four characters. The page also shows which System1 resolves and why.
- **Stored values override the environment.** They are written into the process environment at
  start and after each change, so the agents, triage, System1, the web researcher and the CLI all
  read one place. Removing a stored value restores the deployment's own.
- **Log redaction** reads the environment at log time, so keys stored later are redacted too.
- **Size budgets:** backend 4,600, frontend 1,800, tests 2,800, recorded in `scripts/loc_budget.py`.

## D13. OAuth for MCP connectors such as claude.ai (owner, 2026-11-16)

claude.ai adds remote MCP servers as custom connectors through OAuth 2.1, so lectern is now its
own authorization server. It uses the MCP SDK's handlers (`mcp.server.auth`), with a SQLite-backed
provider (`oauth.py`, `oauth_consent.py`, `oauth_admin.py`, `oauth_routes.py`).

- **Discovery:** `/mcp` (and `/mcp/`) answers 401 with
  `WWW-Authenticate: Bearer resource_metadata="<issuer>/.well-known/oauth-protected-resource/mcp"`.
  The protected-resource metadata names the issuer (`LECTERN_PUBLIC_URL`). The authorization-server
  metadata lists `/authorize`, `/token`, `/register` and `/revoke`, PKCE S256 only, and
  `authorization_response_iss_parameter_supported`.
- **Dynamic client registration** accepts public clients only (no secret). Redirect URIs must be
  loopback or an exact allowed callback: `https://claude.ai/api/mcp/auth_callback` and
  `https://claude.com/api/mcp/auth_callback`, plus `LECTERN_OAUTH_REDIRECTS`. Registration is
  limited per IP.
- **Consent:** `/authorize` stores a 10-minute transaction and sends the browser to
  `/connect/authorize?txn=…` in the web app. The signed-in user approves or denies. The transaction
  is bound to that browser by a cookie and can be claimed once. Redirects back carry `iss`.
- **Tokens:** single-use codes; access tokens `lectern_oa_…` (1 hour); refresh tokens
  `lectern_or_…` (30 days) that rotate, where reusing a rotated one revokes the whole family. All
  are stored as sha256 hashes.
- **Every MCP request** checks again that the token is live, the grant is not revoked, the client
  is not disabled and the user is active.
- **Revocation:** people end their own connections (`/me/connections`); admins see and end all
  connections and disable clients (`/admin/oauth/…`). `/revoke` works for public clients: the SDK
  expects a client_secret field, so lectern supplies an empty one.
- **Personal access tokens** still work for Claude Code and scripts.
- **Static serving:** the web app's own routes (`/connect/authorize`, …) are served with
  `index.html`.
- **One scope** (`lectern`): a connection acts as the user. Configurable levers, row-level
  security and multiple resources were left out.

## D14. Sharing decks, per-viewer threads and slide edits (owner, 2026-11-16)

- **Visibility:** each deck is `private` (the default: signed-in users only), `public` (anyone with
  the link) or `password` (public after entering the deck's password once). Signed-in users set it
  (`PUT /decks/{d}/sharing`, MCP `share_deck`).
- **Password decks:** `POST /decks/{d}/unlock` sets a cookie derived from the password's scrypt
  hash, so changing the password locks everyone out again. Unlocking is limited per IP.
- **What a visitor may do** on a deck they can see: read the deck, its slides' threads, DNA,
  influences and traces; ask a slide or the deck; follow their jobs. Everything else (editing,
  uploads, sharing, influences, files, admin) still needs a session. `GET /decks` shows a
  visitor only shared decks. Visitors' questions count against the per-IP limits and the daily
  budget.
- **Threads are per viewer:** a signed-in user's are theirs; an anonymous visitor gets a random
  `lectern_viewer` cookie; MCP calls use their token owner's. With login off, the single local
  user shares the threads as before. Memory (source M) still learns from every answered question.
- **Slide edits:** `PATCH /decks/{d}/slides/{n}` and MCP `edit_slide` change a slide's title or
  notes on any deck. A folder deck's slide keeps them in its file's metadata. (D15 widens this.)

## D15. Managing decks and slides, and drawing decks as they were made (owner, 2026-11-17)

- **Operations, at parity in the web app, REST and MCP:** rename and delete a deck; update a slide's
  title, body, notes or HTML; insert, duplicate, move and delete a slide (`deck_routes.py`, MCP
  `rename_deck`, `delete_deck`, `update_slide`, `insert_slide`, `duplicate_slide`, `move_slide`,
  `delete_slide`; `update_slide` replaces `edit_slide`). Any signed-in user may do them; visitors
  may not. MCP `delete_deck` needs `confirm=true`, so an assistant asks the person first.
- **Deleting a deck** removes its slides, DNA (with history), chats, jobs, traces, attachments,
  registered files and their blobs. Blobs go first, so a storage failure leaves the deck intact.
- **Folder decks** change their files (content, metadata, `meta.order`). **Uploaded decks** change
  their rows and keep the original file as uploaded. Before an uploaded deck's first change each
  slide's lasting id is written down (`slides.ref`), so DNA stays on its slide; chats and jobs are
  renumbered with their slide (`Store.remap_slides`).
- **All or nothing:** an upload whose original cannot be stored is removed again, and a new folder
  deck whose first slide cannot be stored is not created. A blob store the server cannot write is
  a 503 ("file storage is not writable"), logged at startup and shown on `/health` (still 200,
  `"status": "degraded"`). The image now creates `/data/blobs` owned by the server's user.
- **HTML decks keep their document:** ingest keeps a deck `shell` (the `<head>` with its
  stylesheets, fonts and scripts, the `<html>`/`<body>` attributes, the wrappers around the first
  slide such as `.reveal > .slides`, and the body's scripts). Each slide is shown in the shell, so
  reveal.js decks and styled artifacts look as built, one slide per sandboxed frame.
- **PowerPoint decks are drawn:** shapes, text and pictures are placed absolutely on a 960 px
  stage (`ingest/pptx_html.py`); pictures are stored as files and served at
  `/media/{deck}/{name}`, whose unguessable name is the permission (a sandboxed frame sends no
  cookies). Theme colours and fonts fall back to defaults; `GET /decks/{d}/original` downloads
  the exact file. A LibreOffice renderer was left out as too heavy for now.
